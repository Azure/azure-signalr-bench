# TSG 库元规范（Meta Specification & Agent Guardrails）

本文档定义 `tsg/` 排障知识库的分层架构、写作模板与演进红线。**任何人类开发者或 AI Agent 在新增、修改本目录下的文档前，必须先阅读并严格遵守本规范。**

---

## 1. 为什么要正交分层（核心设计哲学）

传统排障文档最大的腐化来源，是写成**“一次事故一篇流水账”**（例如 `2026-11-12-wps-p2p-message-loss.md`）：
- 后人遇到现象时，不知道该翻哪篇历史记录；
- 同一套查日志、看监控、算重连的方法在十几个文件里反复复制粘贴，久而久之口径互相矛盾；
- AI Agent 后续维护时极易往文件末尾无脑追加个案，把知识库变成不可读的日志坟场。

因此，本库强制拆分为**两个正交维度**，排障时通过二维组合定位根因：

```text
维度 A：现象路由层 (symptoms/)          维度 B：取证与避坑层 (debugging/)
“我在 Report 看到了什么异常？”   ───►   “我去哪个平面怎么查？有哪些度量坑？”
  ├─ connection-failures.md               ├─ methodology-and-pitfalls.md
  ├─ pod-lifecycle-and-control.md         ├─ aks-logs-and-nodes.md
  ├─ message-loss-and-reconnects.md       └─ service-metrics-and-sdks.md
  └─ high-latency.md
```

- **`symptoms/`（按可观测结果切分，MECE 互斥完备）**：只回答**“看到某类红/黄现象时，有哪些候选机制、靠什么区分信号分流”**。不按测试名切分，也不内联大段查询脚本。
- **`debugging/`（按取证平面与方法切分，跨现象复用）**：只回答**“怎么查集群/服务/代码计数、指标真实语义是什么、有哪些反直觉陷阱”**。一处维护，所有现象页通过相对链接引用。

## 2. 文档结构契约（Schema Templates）

### 2.1 `symptoms/*.md` 必须包含且仅包含以下三节

1. **`## 1. 现象特征（Observable Signature）`**
   - 明确列出 Portal Report、`CheckFailures`、`ErrorSummary` 或 `TestRunner` 状态中的精确判定条件与对应代码位置。
2. **`## 2. 快速分流表（Triage Matrix）`**
   - 一张 Markdown 表格，列固定为：`区分信号 | 优先怀疑方向 | 取证动作（链接到 debugging/）`。
   - 读者在 30 秒内能根据手头现象选出下一步唯一动作。
3. **`## 3. 已验证机制目录（Verified Mechanisms）`**
   - 每个根因机制必须使用统一的五元组卡片，缺一不可：
     - **故障域**：`Service` | `Infra / AKS` | `Harness / SDK` | `Scheduling / Operator`
     - **作用机制**：用一句话写清因果链 `A → B → C`。
     - **确诊判据**：必须满足哪些可观测/定量证据才能下结论。
     - **排除判据**：看到什么证据即可立即排除该机制（防止先入为主）。
     - **典型锚点**（可选，≤ 2 行）：简短注明曾验证过的配置或修复提交，严禁展开写事故故事。

### 2.2 `debugging/*.md` 必须包含且仅包含以下三节

1. **`## 1. 适用问题（Questions Answered）`**
   - 简述本页方法用于回答哪几类未知问题。
2. **`## 2. 标准取证动作（Standard Probes）`**
   - 可直接复用的查询模板、命令或代码核对入口（作为全库唯一事实源）。
3. **`## 3. 已知坑点（Pitfalls & Anti-Patterns）`**
   - 每条坑点固定采用三段式：
     - **误区（Trap）**：容易犯的错误推断或错误操作。
     - **真相（Reality）**：底层代码、协议或监控系统的真实行为。
     - **铁律（Rule）**：实操时必须执行的核对动作。

## 3. 面向未来维护者与 AI Agent 的硬性红线（Anti-Corruption Rules）

1. **严禁新建个案/测试专篇**
   - 禁止创建 `incident-*.md`、`YYYYMMDD-*.md` 或 `<test-name>.md`。
   - 新发现的问题必须拆解沉淀：**新现象特征**归入 `symptoms/`，**新取证手段或新坑点**归入 `debugging/`。
2. **严禁跨层复制粘贴查询语句**
   - KQL 查询、Azure Monitor CLI、指标维度解释只允许写在 `debugging/` 中；`symptoms/` 必须用相对链接指向对应小节。
3. **严禁把“发现局部缺陷/重连”直接写成“主因”（数量级闭合原则）**
   - 写入任何机制前，必须经过定量对账（例如：10 次短暂重连解释不了 30% 的消息缺口；存在未 `await` 的代码隐患不等于本次真的发生了请求失败）。不满足数量级闭合的只能标为 `[待验证假设]`，不得混入已验证机制。
4. **严禁未经证实的推测入库**
   - 只记录已被线上监控/日志对账或本地最小复现证实的事实；临时环境状态（如某天某台临时节点名）只可作为 1 行锚点示例，不得写成永久定论。
5. **谨慎扩容文件数量**
   - 仅当出现现有 4 类现象或 3 个取证平面完全无法涵盖的全新正交分类时，才允许新增文件，且必须同步更新 [`README.md`](./README.md) 索引表。
